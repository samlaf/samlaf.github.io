Every guarantee a system makes holds under a failure model: "durable, while at most f nodes crash," or "p99 under 50 ms, while one node is down." Most writing on distributed systems fixes the failure model early and never revisits it. Machines crash, networks drop messages, and sometimes a node lies. But the faults that cause the most outages are not on that list. They are bugs that run on every replica at once, and people who push a bad config or run the wrong command.

This post asks who can fail, and which defenses work against each. The short answer: replication masks the faults that strike one copy at a time, and it copies every other fault faithfully.

## Fault, error, failure

[Avižienis, Laprie, Randell, and Landwehr][avizienis] (2004) give the standard vocabulary, and it separates three things that everyday speech blurs:

- A **fault** is the cause: a dead disk, a bug, a typo in a config.
- An **error** is the wrong state the fault produces: a corrupted page, a replica with the wrong value.
- A **failure** is when the service a user sees goes wrong: a lost write, a timeout, a wrong answer.

A fault need not cause an error, and an error need not cause a failure. Fault tolerance is everything that stops the chain before the last link.

## Mask, or detect and recover

In the same taxonomy, fault tolerance is the goal, and it has two means:

- **Masking:** enough redundancy that the error never reaches the user, whether anyone notices it or not. A quorum write that succeeds on four of six copies masks a dead fifth and sixth.
- **Detecting and recovering:** notice the error, then fix the state. Recovery rolls back to a good state, rolls forward to a new one, or reconfigures around the faulty part: elect a new leader, remove the dead replica.

So tolerance is not a third thing beside masking and detection. It is the name for both. Papers sometimes list detection, masking, and tolerance side by side, as the [DMT router mechanism][dmt] (PDP 2015) does. There "tolerance" means recovery: keep routing after a detected fault, without disabling the router.

[Miller's replication spectrum][miller-spectrum] is this split applied to replication. Quorums mask a failed replica: the survivors carry on. Reconfiguration detects it: the group stalls until the failed node is replaced. Raft masks a follower's failure and detects its leader's.

Masking still needs detection, just not on the request path. Each masked fault uses up some redundancy. A quorum of six that has quietly lost three copies still answers, but one more fault breaks it. The taxonomy warns about exactly this: masking can hide a growing loss of redundancy. So masked systems still detect and repair in the background, through anti-entropy, health checks, and replacing dead nodes. The difference is that no request waits for it.

## Who fails

The failure model says what the environment may do. It also says who:

| Who fails | Example | What masks it | What doesn't |
| --- | --- | --- | --- |
| A machine | a crash, a lost disk | replication: independent copies | — |
| The network | a partition, a delay | quorums, timeouts | — |
| A node that lies | a Byzantine fault | 3f + 1 replicas, signatures | — |
| Software | the same bug on every replica | staged rollouts, version diversity | replication: every copy runs the same code |
| A person | a bad config, a bad deploy, `DROP TABLE` | canaries, staged rollouts, delayed replicas, backups, undo | replication: it copies the mistake |

The first three rows are the classic failure models, and they share one assumption: faults are independent. One machine's crash says nothing about the next one's. That is what makes redundancy work.

The last two rows break that assumption. A bug lives in the code, and every replica runs the same code. A config push reaches every node it targets. These faults are correlated by construction.

## Replication copies mistakes

Replication's whole job is to make every copy the same. Against an independent fault, that is the defense: the other copies still hold the data. Against a correlated fault, it is the attack path. An operator's `DROP TABLE` commits on the primary and replicates to every follower within milliseconds. A bug that corrupts rows corrupts them everywhere. The more faithfully a system replicates, the faster it spreads the mistake.

So the defenses against software and people work along the two axes replication doesn't use: time and space.

## Defenses in time

Keep the past, so that a mistake can be undone:

- **Immutable data and recomputation.** In [Human Fault-tolerance][marz-talk] (Strata 2013), Nathan Marz argues that human mistakes are the faults that matter most, and that a mutable database can't recover from them. If the raw data is append-only, a bad deploy can corrupt only derived views, and fixing the code and recomputing undoes the damage. This is the reasoning behind his Lambda architecture, and behind event sourcing.
- **Backups and point-in-time recovery.** Restore the database as of the moment before the mistake.
- **Delayed replicas.** A replica that applies the log an hour late still holds the table that the primary just dropped. MySQL and Postgres both support this.
- **Multiversion storage.** Old versions kept for concurrency control double as an undo history, for as long as garbage collection keeps them.

## Defenses in space

Limit how far one mistake can reach:

- **Staged rollouts and canaries.** Push a change to one machine, then one zone, then everywhere, and watch at each step. A bad change fails small.
- **Cells.** Split the system into independent copies of the whole stack, each serving a slice of the users. A bad push to one cell can't reach the others. This is splitting used for safety rather than scale: [Carving a database at its joints](/programming/carving-a-database-at-its-joints.html) notes that with splitting, a failure stays in one slice.
- **Shuffle sharding.** TODO: [AWS][aws-shuffle] assigns each customer a random subset of workers, so one bad customer's load takes down few others.

The two axes trade off. Replication spreads a write to every copy as fast as possible. Staged rollouts spread a change as slowly as is safe. A system needs both, for different kinds of change: data should spread fast, and code and config should spread slowly.

## Make mistakes hard to make

The cheapest fault is the one that never happens. [Error-tolerant design][error-tolerant] builds that into the interface: undo instead of confirmation dialogs, constraints that make the wrong action impossible (the Japanese term is *poka-yoke*, mistake-proofing), and actions that are easy to reverse. For operators, that means typed and validated configs, dry runs, and tools that show what a change will do before it does it.

[DDIA][ddia] files human errors under reliability, next to hardware faults and software errors, and recommends the same mix: make mistakes hard, isolate where they can strike, recover quickly, and monitor.
